## Règles du sprint 34

1. **Tests** seulement via `WORKER_ID=<worker> TEST_DB_NAME=b2b_<worker> TEST_CACHE_DIR=var/cache-<worker> bin/run-tests <arguments PHPUnit>`. Jamais `phpunit` en direct. **Pour US-210, US-221, US-229 : aucun test (spikes sans code dans la démo).**
2. **Disque** : **aucun test ni rendu local sous 5 Go libres** (registre du 2026-10-28 : 4 Go au lancement) ; **aucune suite complète sous 6 Go** ; `bin/check-disk` avant chaque lot ; mémoire libre et swap relevés. Sous le seuil, le worker écrit tests et code mais ne lance rien, le dit dans son rapport et prépare la tâche suivante. Une seule suite complète à la fois.
3. **Un seul cache de rendu par worker** : `bin/render-page` réutilise le même cache, avec `bin/check-disk` avant chaque rendu ; aucun rendu sous le seuil ; aucun rendu en série sans nettoyage ni relevé de l'espace libre. **US-210, US-221, US-229 : aucun rendu (spikes).**
4. **Jamais de fichier `.env*`** (lecture, création, copie), dans la démo comme dans le dépôt du thème.
5. **Aucun `rm` refusé contourné** ni aucun refus d'outil contourné par un autre chemin : le noter dans le rapport, avec la commande refusée, et continuer.
6. **Branche `feature/sprint-34-spikes-et-theme`** (arbre principal, déjà créée) pour la démo ; **pas de checkout dans l'arbre partagé**. Pour le dépôt du thème (US-222) : branche `feature/theme-tranche-1` créée par le worker après la création du dépôt par l'orchestrateur.
7. **Commits limités aux chemins nommés** : `git add <nouveaux fichiers>` puis `git commit -m "…" -- <chemins>` ; jamais `git commit -a` ni index partagé ; `git show --stat` avant chaque push. Commits Conventional Commits **avec le bon numéro de story** (US-210, US-221, US-222 ou US-229), relu contre la branche et la PR par `git log -1` avant le push.
8. **Pas de push, de tag, de release ni de PR sans la demande de l'orchestrateur** ; aucune commande Railway. **Exception décidée au registre le 2026-10-28 (auteur : Thibaut, règle 30)** : pour le dépôt du thème d'US-222 seulement, **l'orchestrateur crée le dépôt public durci** ; le worker pousse sa branche `feature/theme-tranche-1`, ouvre la PR ; **l'orchestrateur fusionne CI verte** ; **jamais de tag ni de release** ; le worker ne crée aucun dépôt et ne fusionne pas. Le dépôt de la démo reste soumis à la règle générale.
9. **Pas de maquette ce sprint.** Porte de Thibaut : le GO de l'ADR d'US-221 (T-221-03) avant de lancer US-222, noté au [registre](./registre-decisions.md) ; les autres ADR (US-210, US-229) sont relus au fil de l'eau.
10. **Aucun plugin modifié ce sprint** ; `composer.lock` de la démo inchangé. Aucune valeur écrite en dur dans un gabarit ou une traduction : les jetons du thème sont surchargeables.
11. **Aucun identifiant saisi en production** ; **aucune action chez un moteur de recherche** ; Claude ne touche à aucun compte (Search Console, GitHub hors dépôt du thème).
12. **Ton neutre**, aucune comparaison avec Sylius Plus ni mention de l'offre de l'éditeur (politique de communication) ; **aucun détail de sécurité dans les dépôts publics** (démo et thème) : ADR, descriptions de PR et messages de commit ne citent ni secret, ni seuil, ni route d'administration, ni constat détaillé ; **note privée de sécurité (US-210) hors dépôt public** ; formulation prudente du DPP (US-229 : jamais « conforme » ni « certifié »).
13. **Test rouge commité seul** (US-222), cité dans la PR ; `bin/proof-rebase` (ou, à défaut, rebase puis `php bin/proof-refresh` et `php bin/proof-check`) si la PR ajoute ou supprime un fichier de tests ; PR de la démo fusionnées en série.
14. **Contrôle complet avant de rendre la main** : PHPStan sur tout le dépôt (`php -d memory_limit=2G vendor/bin/phpstan analyse`, `src` et `tests`), ECS (`src tests`), Rector, lint Twig et YAML ; aucun compteur écrit en dur. **US-210, US-221, US-229 : aucune commande (spikes sans code dans la démo) ; US-222 : PHPStan, ECS, Rector du dépôt du thème.**
15. **Mesures de production consignées le jour du déploiement** dans le fichier de tâches pour ce qui est public (US-207 du sprint 33 : `robots.txt`, en-têtes, `sitemap.xml`, pa11y, 320, 375 et 1280 px).
16. **« Que devient cet état après un déploiement ? »** : tout fichier, répertoire, cache ou variable d'environnement hors base est décrit (conteneur ou volume, ce qui le recrée au démarrage) et vérifié dans un conteneur neuf avant le merge. Le conteneur est neuf à chaque déploiement, la base survit. Ce sprint : **aucune variable d'environnement nouvelle dans la démo** ; le dépôt du thème est créé une fois, à son URL définitive.
17. Les autres règles du gabarit (nettoyage de ses propres ressources, attente bornée, lecture sans filtrage, pas de `git` dans un worktree isolé, secrets fictifs) restent applicables.
18. **Aucune commande récursive ou destructive sur un chemin non vérifié** (incident du 2026-10-25 : `cp -Rn "$D"/. …` avec `$D` vide avait copié la racine du Mac). Jamais de `cp -R`, `rm -rf` ni `mv` sur un chemin issu d'une variable ou d'un glob sans :
    ```sh
    set -u
    D="…"
    [ -n "$D" ] && [ -d "$D" ] || { echo "chemin vide ou absent" >&2; exit 1; }
    case "$D" in "$PWD"/*) ;; *) echo "hors du dossier attendu" >&2; exit 1 ;; esac
    ```
    Le chemin est aussi vérifié sous le dossier attendu ; un glob sans résultat est traité comme vide. L'orchestrateur n'approuve aucune commande sans cette garde. Les commandes de nettoyage destinées à Thibaut sont en **chemins absolus**, précédées d'un `du -sh`.
19. **Rejouer la séquence exacte de la CI avant de rendre la main** : la préparation de la CI (installation, fixtures, base) est rejouée telle quelle en local avant le push, quand le disque le permet ; la dernière ligne de sortie est citée. **Pour US-222, la CI du dépôt du thème juge** : la PR n'est fusionnée qu'au vert, run terminé.
20. **Aucune fusion avec une question ouverte** : avant tout enchaînement automatique de fusion, vérifier qu'aucune question à Thibaut n'est en suspens sur la PR (commentaire ou description) ; sinon la PR reste ouverte. **Toute décision ou tout GO est noté au registre avec son auteur** ; une phrase « accepté par Thibaut » n'est écrite que si elle y figure.
21. **Fichiers communs déclarés et attribués** (incident du sprint 29 : un commit avait embarqué les lignes d'un autre worker) : un fichier commun n'est commité qu'après `git diff -- <fichier>` relu ; il ne contient que ses lignes, sinon le worker attend et prévient l'orchestrateur. Matrice : [tasks/README.md](./tasks/README.md).
22. **Aucun test depuis un worktree dont `vendor` est un lien symbolique** : l'autoload de Composer résout le lien et exécute le code de l'arbre principal. Les tests se lancent dans l'arbre partagé.
23. **Captures réelles, relues à 1280 px avant la PR** : captures par `bin/render-page` avec les vignettes `b2b_photo*` ; si le rendu local est impossible faute de disque, captures de production (pages publiques, sans connexion), relues et dites dans la PR ; l'orchestrateur relit à 1280 px la home connectée et chaque page touchée avant d'ouvrir la PR ; un bloc à nombre fixe d'éléments a un test qui les compte. **US-210, US-221, US-222, US-229 : aucune capture (spikes ou extraction sans modifier le rendu de la démo).**
24. **Parallélisme réglé sur la machine** : avant de lancer les workers, l'orchestrateur relève `df -h /`, la mémoire libre et le swap ; **au-delà de 2 Go de swap ou sous 7 Go de disque, au plus deux workers lancent des tests en même temps**. Le seuil se mesure avec `df`, jamais avec le Finder. Un worker qui n'a pas la main sur les tests le dit dans son rapport et prépare la tâche suivante.
25. **Échanges avec l'orchestrateur** : chaque réponse de l'orchestrateur à un worker cite l'**identifiant de la décision** (commit du registre) ; le worker ignore sans relance une notification d'attente antérieure à cette réponse. **`vendor/` de l'arbre partagé** : aucun worker n'y lance `composer install`, `composer update` ni `composer require`.
26. **Registre avant toute PR hors sprint ; relecture avant d'attendre** : tout correctif hors sprint (PR séparée) a sa ligne au [registre](./registre-decisions.md) **avant** l'ouverture de la PR, avec la date, l'auteur et la tâche ; un worker qui s'apprête à écrire « j'attends » **relit d'abord le registre et ses messages reçus**, et ne signale son attente que si aucune réponse ne la lève.
27. **Rouge prouvé** (action 1 de la rétro du sprint 32, incident : les fournisseurs de données des tests rouges d'US-205 étaient faux et corrigés dans le commit du code, donc ces tests n'avaient pas été vus rouges ; ceux d'US-206 avaient été corrigés deux fois) : avant de commiter des tests rouges, le worker (a) **relit les fournisseurs de données** (`#[DataProvider]` : les valeurs attendues, les pages, les locales), (b) **exécute les tests** par `bin/run-tests` et (c) **cite dans le message du commit la ligne d'échec de chaque test** (assertion ou exception, pas seulement « FAIL »), en vérifiant que l'échec vient de la fonctionnalité absente et non d'une donnée de test fausse. **Aucune correction des données d'un test rouge dans le commit du code** : une erreur trouvée plus tard donne un commit de test séparé, noté dans la PR. Si le disque empêche l'exécution (règle 2), le worker le dit dans le message du commit et dans son rapport, et la story n'est **pas comptée « rouge prouvé »** (noté au task-board). **US-222 seulement (spike sans code dans la démo).**
28. **Table « invariants de test » au cadrage** (action 2 de la rétro du sprint 32, incident : un conflit entre une maquette et un test « non modifié » n'a été vu qu'à l'implémentation) : la tâche de cadrage de chaque story liste, dans le fichier de tâches, **chaque test existant que la story touche** (assertion, fournisseur de données, fixture, script du runbook), ce qu'il fige aujourd'hui, ce que la story change, le traitement (inchangé, adapté ou nouveau test) et, pour toute adaptation, la **ligne du registre qui la décide avant l'action**. L'orchestrateur confronte la table au périmètre avant le premier commit de code ; tout conflit est noté au registre avec ses options. DoD : 0 test existant modifié sans ligne de registre, 0 conflit découvert après le démarrage du code. **US-222 seulement (spikes sans code) ; table préremplie dans [tasks/US-222-tasks.md](./tasks/US-222-tasks.md), à confirmer par T-222-01.**
29. **Dépôts de plugins : « plugin-repo-branch-check » et périmètre** (mémoire du projet, incident des branches fusionnées périmées ; GO du registre du 2026-10-28) : **dans chaque dépôt, avant tout commit**, `git fetch origin`, puis contrôle de la branche courante (`git branch --show-current`) et de son retard sur la branche par défaut distante ; une branche déjà fusionnée ou en retard est abandonnée au profit d'une nouvelle branche créée depuis `origin/<branche par défaut>`. **Ce sprint : US-222 crée un dépôt neuf, aucun contrôle nécessaire.**
30. **GO transmis avant consignation** (action 1 de la rétro du sprint 33, incident : le classifieur a refusé une boucle de fusions à w209 ; Thibaut a répondu « tu peux fusionner » à l'orchestrateur, consigné comme « l'orchestrateur fusionne » ; w209 avait déjà fusionné 22 PR lui-même quand les consignes contraires sont arrivées) : **toute règle d'exécution d'un GO** (qui crée le dépôt, qui pousse, qui fusionne) **est transmise au worker concerné avant ou en même temps que son inscription au registre** ; **un GO donné à l'orchestrateur ne se délègue au worker que par une phrase explicite**. Ce sprint : le registre du 2026-10-28 (auteur : Thibaut) dit « l'orchestrateur crée le dépôt et fusionne » pour US-222 ; le worker pousse sa branche et ouvre la PR, il ne crée aucun dépôt et ne fusionne pas.
