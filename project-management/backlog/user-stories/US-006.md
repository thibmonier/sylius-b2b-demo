# US-006 — Spike : mode worker FrankenPHP

> Epic : [EPIC-01](../epics/EPIC-01.md) · Persona : Thibaut · MoSCoW : **Should** · Points : **2** · Sprint : 9
> Dépendances : US-002

## Story

En tant que Thibaut, je veux savoir si le mode worker FrankenPHP est sûr avec Sylius et les plugins, afin de gagner en performance sans fuite d'état.

## Valeur

Performance (NFR-1).

## Critères d'acceptation

```gherkin
Fonctionnalité: Spike : mode worker FrankenPHP

  Scénario: Décision
    Quand je lance la démo en mode worker et les tests de fumée
    Alors je documente le gain mesuré et les services à état éventuels
    Et une ADR décide du mode retenu

  Scénario: Threads bornés
    Étant donné le Caddyfile de la démo
    Quand FrankenPHP démarre, en mode classique ou en mode worker
    Alors le nombre de threads est borné explicitement (num_threads / max_threads)
    Et la mémoire du conteneur reste sous la limite du service Railway, cron supercronic compris

  Scénario: Mesure comparée
    Étant donné les mêmes pages (accueil B2B, catégorie, fiche produit, panier) et la même charge
    Quand je les mesure en mode classique puis en mode worker
    Alors la latence (p50, p95) et la mémoire des deux modes sont consignées dans l'ADR

  Scénario: Fuite d'état entre requêtes
    Étant donné le mode worker
    Quand deux visiteurs se succèdent sur le même worker (canal B2B puis B2C, client connecté puis anonyme)
    Alors aucun état (canal, client, panier, locale, porte de démo) ne passe d'une requête à l'autre
    Et toute fuite détectée est documentée avec le service en cause

  Scénario: Repli en mode classique
    Étant donné une fuite d'état non corrigée ou un gain non significatif
    Quand l'ADR conclut
    Alors la démo reste en mode classique avec les threads bornés, et le mode worker n'est pas activé en production
```

## Notes

Repli : mode classique.
