# US-066 — Préparation du sous-domaine de la démo

> Epic : [EPIC-09](../epics/EPIC-09.md) · Persona : Thibaut · MoSCoW : **Should** · Points : **2** · Sprint : 13
> Dépendances : US-052 (ouverture publique, runbook) ; préfixe du sous-domaine fixé à `sylius-b2b` (décision du 2026-10-17) ; domaine du site inconnu, URL complète en US-068

## Story

En tant que Thibaut, je veux que la démo soit prête à répondre sur un sous-domaine de mon site (hôtes de confiance, runbook, références) et que le certificat soit vérifié, afin de remplacer l'URL provisoire Railway sans coupure.

## Contexte

Décision D4 : l'utilisateur crée lui-même le CNAME et le domaine personnalisé dans Railway. Claude prépare `TRUSTED_HOSTS` (`.railway/railway.ts` accepte aujourd'hui `RAILWAY_PUBLIC_DOMAIN` et `healthcheck.railway.app`), le runbook et les références à l'URL, puis vérifie le certificat. Décision du 2026-10-17 : le sous-domaine a le préfixe `sylius-b2b` (`sylius-b2b.<domaine du site>`). Le domaine du site n'est pas connu et l'URL complète arrivera avec lui, en US-068 : le code et les docs utilisent un paramètre (préfixe `sylius-b2b` en valeur de référence, domaine en paramètre), jamais le domaine codé en dur. Tant que la démo est privée, les README pointent vers le dépôt public (US-064) ; l'URL en ligne est ajoutée à la bascule.

## Périmètre

- Analyse des endroits où l'hôte compte : `TRUSTED_HOSTS`, cookies et sessions, URL absolues (e-mails, MCP, OAuth), robots, sitemap, liens de la page Plugins.
- `.railway/railway.ts` : domaine personnalisé en plus du domaine Railway (variable dédiée sans valeur secrète), les deux acceptés pendant la transition.
- Runbook `docs/sous-domaine-demo.md` : étapes de l'utilisateur (CNAME, domaine personnalisé Railway), vérification du certificat, retour arrière, transition.
- Références à l'URL dans les docs existantes (`ouverture-publique.md`, `deploiement-railway.md`, `mcp.md`) sous forme de paramètre.
- Hors périmètre : toute commande Railway, tout changement DNS (utilisateur), tout achat de domaine.

## Critères d'acceptation

```gherkin
Fonctionnalité: Sous-domaine de la démo

  Scénario: Les deux hôtes sont acceptés pendant la transition (nominal)
    Étant donné TRUSTED_HOSTS configuré avec le domaine Railway et le sous-domaine
    Quand une requête arrive sur l'un ou l'autre
    Alors elle est servie normalement
    Et le healthcheck Railway reste accepté

  Scénario: Un hôte inconnu reste refusé (alternatif)
    Étant donné la même configuration
    Quand une requête arrive avec un hôte quelconque
    Alors la réponse est 400 comme aujourd'hui

  Scénario: Le sous-domaine n'est pas encore défini (alternatif)
    Étant donné aucune valeur de sous-domaine
    Quand la configuration est évaluée
    Alors seul le domaine Railway est accepté
    Et aucune valeur n'est codée en dur dans le dépôt

  Scénario: Le certificat n'est pas encore émis (erreur)
    Étant donné le CNAME créé par l'utilisateur
    Quand le certificat est vérifié
    Alors l'écart (délai, CNAME incorrect) est rapporté avec la commande de diagnostic du runbook
    Et rien n'est modifié côté Railway par Claude

  Scénario: Une URL absolue pointe encore vers l'ancien hôte (erreur)
    Étant donné le sous-domaine actif
    Quand les e-mails de démo, la page MCP et les liens absolus sont contrôlés
    Alors chaque lien utilise l'hôte courant ou le paramètre, jamais l'hôte provisoire figé
```
