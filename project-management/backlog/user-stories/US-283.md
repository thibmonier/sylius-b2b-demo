# US-283 — Plugin einvoice-pennylane : premier adaptateur réel de transmission, vers la plateforme agréée Pennylane

> Epic : [EPIC-14](../epics/EPIC-14.md) · Persona : Nadia (responsable e-commerce B2B) · MoSCoW : **Should** · Points : **5** · Sprint : sprint 55 (lancé le 2026-11-12) · Statut : **ready-for-dev**
> Origine : analyse de l'écosystème Sylius du 2026-11-12, suite du spike US-132 (e-invoicing FR, PA/PDP). Nouveau plugin `tmonier/sylius-einvoice-pennylane-plugin`.

## Story

En tant que Nadia, je veux que chaque facture Factur-X générée par la boutique soit transmise à Pennylane et que son statut de transmission soit visible dans l'administration, afin de respecter l'obligation de facturation électronique sans ressaisie ni export manuel.

## Contexte

- `einvoice-transmission` fournit le port `InvoiceTransmitterInterface`, le journal et l'écouteur idempotent, mais **seulement un adaptateur nul** : la chaîne Factur-X → plateforme n'est branchée sur aucune plateforme réelle. Cette story livre le premier adaptateur réel.
- Pennylane est immatriculée plateforme agréée (PA) par la DGFiP à titre définitif depuis décembre 2025, selon [Pennylane](https://www.pennylane.com/fr/fiches-pratiques/facture-electronique/pdp) et des comparateurs ([ma-facture-electronique.org](https://ma-facture-electronique.org/plateforme-agreee/liste-officielle/pennylane/)), sources non indépendantes. **À confirmer sur la liste officielle de la DGFiP au cadrage.** Échéances : réception obligatoire et grandes entreprises/ETI au 1er septembre 2026, PME au 1er septembre 2027.
- Recherche du 2026-11-12 : **aucun connecteur Sylius ↔ Pennylane trouvé** (Packagist, Sylius Addons). Il existe une intégration WordPress et une automatisation Pipedream pour Shopify, sans connecteur natif.
- API Pennylane v2 ([documentation](https://pennylane.readme.io/docs/customer-invoicing)) :
  - le client doit exister avant la facture, recherché par `external_reference` (le code client Sylius) puis créé si absent ;
  - import des factures électroniques par les points d'accès dédiés `/customer_invoices/e_invoices/imports` ([changelog](https://pennylane.readme.io/changelog/customer-supplier-invoices-dedicated-e-invoice-import-endpoints)), qui renvoient l'identifiant de la facture ;
  - jeton d'API avec la portée `customer_invoices:all`, bac à sable disponible pour les tests.
  - Le choix entre import du Factur-X et création à partir de données structurées est à trancher au cadrage. L'import est préféré : le Factur-X de `facturx` reste la source unique.
- Paquet séparé, pour que `einvoice-transmission` reste sans dépendance HTTP ni fournisseur ; d'autres adaptateurs PA pourront suivre sur le même modèle.
- Politique Plus : aucun recoupement (Sylius Plus n'a pas de facturation électronique française), donc plugin promouvable.
- Sécurité : jeton d'API dans une variable d'environnement ou le coffre de secrets, jamais en base ni dans les journaux ; un seul hôte appelé (configuration, pas d'URL saisie) ; message d'erreur du journal nettoyé (aucun jeton, aucune donnée de facture complète).

## Critères d'acceptation

```gherkin
Fonctionnalité: Transmission des factures électroniques à Pennylane

  Scénario: Facture transmise (nominal)
    Étant donné l'adaptateur Pennylane configuré avec un jeton valide
    Et un client dont le code n'existe pas encore dans Pennylane
    Quand le plugin Factur-X génère la facture d'une commande
    Alors le client est créé dans Pennylane avec le code Sylius en external_reference
    Et le Factur-X est importé dans Pennylane
    Et la ligne du journal passe au statut « transmise » avec l'identifiant Pennylane de la facture

  Scénario: Client déjà connu (alternatif)
    Étant donné un client déjà présent dans Pennylane avec le même external_reference
    Quand une nouvelle facture est générée
    Alors aucun doublon de client n'est créé et la facture lui est rattachée

  Scénario: Relance après erreur (alternatif)
    Étant donné une facture au statut « error » dans le journal
    Quand un administrateur la relance (RelaunchTransmissionHandler)
    Alors elle est transmise une seule fois et le journal est mis à jour

  Scénario: Jeton invalide ou portée insuffisante (erreur)
    Étant donné un jeton refusé par Pennylane (401 ou 403)
    Quand une facture est générée
    Alors la facture reste générée, la ligne du journal passe à « error » avec un message sans le jeton
    Et aucune nouvelle tentative automatique n'est faite tant que la configuration n'est pas corrigée

  Scénario: Pennylane indisponible ou quota atteint (erreur)
    Étant donné une réponse 5xx, 429 ou un délai dépassé
    Quand une facture est générée
    Alors la ligne passe à « error » avec un message explicite et la facture peut être relancée
    Et la génération de la facture n'est jamais bloquée
```
