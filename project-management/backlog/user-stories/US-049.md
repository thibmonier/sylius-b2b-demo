# US-049 — Fiabilité de la remise à zéro

> Epic : [EPIC-08](../epics/EPIC-08.md) · Persona : Thibaut · MoSCoW : **Must** · Points : **3** · Sprint : 11
> Dépendances : US-033, US-041, US-048 (livrées)

## Story

En tant que Thibaut, je veux que toute défaillance de la remise à zéro nocturne, y compris une erreur PHP fatale, soit signalée par `/healthz`, afin que le moniteur me prévienne au lieu de laisser une démo à moitié rechargée en apparence saine.

## Contexte

Le 2026-10-17, sur Railway, `app:demo:reset` a échoué avec « Allowed memory size exhausted » pendant `cache:warmup`. Une erreur fatale n'est pas une exception : `ResetStatus::markFailed()` n'est jamais appelé, le marqueur `var/demo-reset-failed` n'est pas écrit et `/healthz` reste 200. Le correctif de la limite mémoire (`-d memory_limit=1G` du crontab, PR #20) traite le symptôme, pas la cause.

## Périmètre

- **Marqueur fiable** : `App\Demo\Command\ResetStatus` pose un état « en cours » dès le début du reset et ne le retire qu'au succès (ou fonction d'arrêt `register_shutdown_function` si l'approche est préférée). Test rouge d'abord.
- **Sous-processus** : `cache:clear` et `cache:warmup` (`DemoResetCommand::stepClearWarmUpCache` / `runSubCommand`) tournent dans un sous-processus à mémoire fraîche, plutôt que dans le processus des fixtures. Le `-d memory_limit=1G` du crontab est conservé.
- **Plafond du corps de requête** : `request_body max_size` dans `docker/Caddyfile` pour `POST /demo/webhooks/receive` (constat mineur de revue du sprint 10 : corps chunked lu avant le contrôle de taille). Test.
- **Calendaire** : T-048-11 (ex T-041-15), relevé de coût Railway complet, pas avant 2026-10-23, par l'utilisateur.
- **Documentation** : `demo_orders` n'atteint pas l'objectif de 1 750 requêtes (1 911, cœur Sylius) ; la limite est actée, sans code.

## Critères d'acceptation

```gherkin
Fonctionnalité: Fiabilité de la remise à zéro

  Scénario: Reset réussi
    Étant donné une démo saine
    Quand app:demo:reset se termine sans erreur
    Alors le marqueur var/demo-reset-failed est absent
    Et /healthz répond 200

  Scénario: Erreur fatale PHP pendant le reset
    Étant donné un reset qui épuise la mémoire PHP pendant le réchauffage du cache
    Quand le processus s'arrête sur l'erreur fatale
    Alors le marqueur var/demo-reset-failed est présent
    Et /healthz répond 503

  Scénario: Cache réchauffé dans un sous-processus
    Étant donné un reset qui a chargé les fixtures
    Quand l'étape de cache s'exécute
    Alors cache:clear et cache:warmup tournent dans un processus distinct de celui des fixtures
    Et la limite mémoire du crontab (1G) reste appliquée

  Scénario: Reset suivant après un échec
    Étant donné un marqueur d'échec laissé par un reset précédent
    Quand le reset suivant réussit
    Alors le marqueur est retiré et /healthz répond 200

  Scénario: Corps de requête trop gros sur le récepteur de webhooks
    Étant donné un POST /demo/webhooks/receive dont le corps dépasse le plafond
    Quand Caddy reçoit la requête, y compris en transfert chunked
    Alors la réponse est 413 sans que PHP lise le corps

  Scénario: Sous-processus de cache en échec
    Étant donné un cache:warmup qui sort avec un code non nul
    Quand le reset l'exécute
    Alors le reset est en échec, le marqueur est posé et /healthz répond 503
```
