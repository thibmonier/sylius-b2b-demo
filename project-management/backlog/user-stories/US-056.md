# US-056 : Plugin équipements : modèles d'équipement liés aux variantes compatibles (admin)

> Epic : [EPIC-14](../epics/EPIC-14.md) · Persona : Sophie (back-office du marchand) · MoSCoW : **Should** · Points : **5** · Sprint : 21
> Dépendances : US-054 (livrée, sprint 12 : squelette, `SPEC.md`, ADR-0001) ; MMF avec US-057 et US-058 ; suite US-059 (publication) et US-060 (démo), sprint 22

## Story

En tant que Sophie, gestionnaire du catalogue d'un distributeur de pièces détachées, je veux créer des modèles d'équipement (« Camion Modèle X ») et indiquer, depuis la fiche d'une variante, les modèles avec lesquels elle est compatible, afin que les clients puissent ensuite retrouver les pièces qui vont avec leurs machines.

## Contexte

Première tranche fonctionnelle du plugin `tmonier/sylius-customer-asset-management-plugin` (dépôt `~/Projects/sylius_plugins/sylius-customer-asset-management-plugin`, aujourd'hui un squelette sans entité). Sources : `SPEC.md` §2 et §3, ADR-0001 (décisions 1, 2 et 6).

Décisions déjà prises (ADR-0001, acceptée le 2026-10-17) :
- table `equipment_model` (code, noms traduits) et table de jointure `equipment_model_variant` (many-to-many vers `sylius_product_variant`, côté propriétaire sur le modèle) ; aucune colonne ajoutée aux entités du cœur ;
- compatibilité **par variante**, pas par produit ;
- index `(equipment_model_id, variant_id)` livré dans la migration ;
- migrations fournies par le plugin et préfixées à la configuration Doctrine, comme les autres plugins.

Périmètre de la story : CRUD des modèles en administration (liste, création, édition, suppression), sélection des modèles compatibles sur le formulaire de la variante, traductions FR et EN, permission d'administration dédiée. **Hors périmètre** : import en masse (`SPEC.md` §6), règles par année ou option, parc des clients (US-057), filtre du catalogue (US-058), toute promotion.

Les modèles d'équipement sont des données du marchand, pas des données personnelles : pas de contrainte RGPD sur cette story.

### Les 3 C

- **Carte** : la story ci-dessus.
- **Conversation** : le code d'un modèle est-il modifiable après création ? Proposition : non, pour ne pas casser une compatibilité déjà saisie (champ en lecture seule à l'édition). La suppression d'un modèle retire ses liens de compatibilité, jamais les variantes (la garde « modèle utilisé par un parc » arrive avec US-057).
- **Confirmation** : les scénarios Gherkin ci-dessous.

## Critères d'acceptation

```gherkin
Fonctionnalité: Modèles d'équipement et compatibilité des variantes

  Scénario: Créer un modèle et l'associer à des variantes (nominal)
    Étant donné que Sophie est connectée à l'administration avec la permission de gérer les modèles d'équipement
    Quand elle crée le modèle de code « TRUCK-X » nommé « Camion Modèle X » (FR) et « Truck model X » (EN)
    Et qu'elle ouvre la variante « Filtre à huile 1 L » et coche « Camion Modèle X » dans « Modèles compatibles »
    Alors le modèle « TRUCK-X » apparaît dans la liste des modèles
    Et la fiche de la variante affiche « Camion Modèle X » comme modèle compatible
    Et la liste des modèles indique 1 variante compatible pour « TRUCK-X »

  Scénario: Associer plusieurs variantes puis en retirer une (alternatif)
    Étant donné le modèle « TRUCK-X » associé aux variantes « Filtre à huile 1 L » et « Filtre à air »
    Quand Sophie décoche « Camion Modèle X » sur la variante « Filtre à air » et enregistre
    Alors « TRUCK-X » n'a plus qu'une variante compatible, « Filtre à huile 1 L »
    Et la variante « Filtre à air » existe toujours dans le catalogue

  Scénario: Nom affiché selon la langue de l'administration (alternatif)
    Étant donné le modèle « TRUCK-X » traduit en français et en anglais
    Quand Sophie ouvre l'administration en anglais
    Alors la liste affiche « Truck model X »
    Et, si la traduction anglaise est absente, elle affiche le code « TRUCK-X » sans erreur

  Scénario: Supprimer un modèle (alternatif)
    Étant donné le modèle « TRUCK-X » associé à 2 variantes
    Quand Sophie le supprime et confirme
    Alors le modèle disparaît de la liste et ses 2 liens de compatibilité sont supprimés
    Et les 2 variantes restent dans le catalogue, intactes

  Scénario: Code déjà utilisé (erreur)
    Étant donné qu'un modèle de code « TRUCK-X » existe
    Quand Sophie en crée un second avec le code « TRUCK-X »
    Alors le formulaire est refusé avec le message « Ce code est déjà utilisé »
    Et le nombre de modèles reste égal à 1

  Scénario: Données invalides (erreur)
    Étant donné le formulaire de création d'un modèle
    Quand Sophie envoie un code vide ou de plus de 64 caractères, ou un nom de plus de 255 caractères
    Alors le formulaire est refusé avec un message par champ en erreur, aucun modèle n'est créé

  Scénario: Utilisateur d'administration sans permission (erreur)
    Étant donné un utilisateur d'administration sans la permission de gérer les modèles d'équipement
    Quand il ouvre l'écran des modèles ou envoie une création
    Alors l'accès lui est refusé (403) et aucune donnée n'est modifiée
```
