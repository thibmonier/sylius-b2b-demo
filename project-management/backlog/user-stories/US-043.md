# US-043 — Statut d'approbation dans le plugin b2b-mcp

> Epic : [EPIC-07](../epics/EPIC-07.md) · Persona : Thibaut · MoSCoW : **Should** · Points : **5** · Sprint : 8
> Dépendances : US-020

## Story

En tant que Thibaut, je veux que le plugin b2b-mcp refuse le consentement OAuth et les appels `/_mcp` d'un client dont le compte n'est pas utilisable, afin que la démo n'ait plus besoin de son propre `McpApprovalGuard`.

## Contexte

Rétro du sprint 7. Le plugin `sylius-b2b-mcp-plugin` ne vérifie que l'activation du compte ; la démo ajoute `App\Demo\Mcp\McpApprovalGuard` (écouteur `kernel.request`, priorité 6) qui refuse les comptes en attente ou rejetés (registration-approval, US-020). Le plugin gagne un point d'extension générique (interface taguée, par exemple un vérificateur d'utilisabilité du compte, `accept`/`refuse` avec motif), **sans dépendance dure** à `sylius-registration-approval-plugin` ; la démo y branche son implémentation puis supprime son écouteur. Publication d'une version mineure après GO explicite de l'utilisateur.

## Critères d'acceptation

```gherkin
Fonctionnalité: Compte utilisable pour le serveur MCP

  Scénario: Compte utilisable
    Étant donné aucun vérificateur refusant le compte d'un client
    Quand le client autorise une application ou appelle /_mcp
    Alors le comportement est inchangé

  Scénario: Consentement refusé
    Étant donné un vérificateur qui refuse le compte (inscription en attente)
    Quand le client ouvre l'écran de consentement OAuth
    Alors le consentement est refusé et aucun code d'autorisation n'est émis

  Scénario: Jeton existant d'un compte devenu inutilisable
    Étant donné un jeton d'accès émis avant le refus et un compte désormais refusé
    Quand l'assistant appelle /_mcp
    Alors la réponse est 403 access_denied, sans en-tête de cache public, et l'appel est journalisé dans l'audit

  Scénario: Vérificateur en erreur
    Étant donné un vérificateur qui lève une exception
    Quand le client appelle /_mcp
    Alors l'accès est refusé par prudence (fail closed) et l'erreur est journalisée sans fuite de détail au client

  Scénario: Jeton forgé ou expiré
    Étant donné un jeton d'accès MCP inconnu, révoqué ou expiré
    Quand le client appelle /_mcp
    Alors la réponse est 401 sans exécuter d'outil, et aucun vérificateur d'utilisabilité n'est appelé avec un client résolu

  Scénario: Plusieurs vérificateurs
    Étant donné deux vérificateurs dont un seul refuse
    Quand le client appelle /_mcp
    Alors l'accès est refusé et le motif du premier refus est journalisé

  Scénario: Publication sans GO
    Étant donné la version validée sans GO explicite de l'utilisateur
    Alors aucune version n'est taguée ni publiée et la démo garde son McpApprovalGuard
```

## Critères SMART

- **Spécifique** : un point d'extension générique, aucune dépendance à registration-approval dans le plugin.
- **Mesurable** : 5 scénarios automatisés dans le plugin et un test de démo ; `McpApprovalGuard` supprimé.
- **Atteignable** : un écouteur et une interface, ≈ 3 points.
- **Réaliste** : s'appuie sur `McpEndpoint` existant.
- **Temporel** : fin du sprint 8 (2026-10-30), publication selon le GO.

## Notes

Le refus du consentement OAuth et celui de `/_mcp` doivent partager le même vérificateur (DRY). Publication d'une version mineure après GO explicite de l'utilisateur.
