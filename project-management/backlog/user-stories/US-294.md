# US-294 — Santé de la plateforme : sondes de données (connexion, migrations en attente, dérive du schéma, tables qui grossissent)

> Epic : [EPIC-21](../epics/EPIC-21.md) · Persona : Didier (DSI) ; Hugo (intégrateur Sylius) · MoSCoW : **Must** · Points : **5** · Sprint : **[sprint 58](../../sprints/sprint-58-donnees-files-cron/sprint-goal.md)** · Statut : **done** (plugin PR #15, fusionnée le 2026-11-26)
> Origine : demande de Thibaut du 2026-11-22 ; périmètre du sprint 58 choisi par Thibaut le 2026-11-25 (EPIC-21 complet). Dépend d'[US-287](US-287.md) (contrat) et d'[US-293](US-293.md) (forme des sondes, seuils configurables, lien de documentation). Première story du sprint.

## Story

En tant que DSI, je veux que la page de santé me dise si la base répond, si une migration a été oubliée, si le schéma a dérivé du code et si une table grossit sans purge, afin de l'apprendre par l'écran avant que la boutique ne tombe sur une colonne absente ou un disque plein.

## Contexte

Catégorie `data` (déjà présente dans `HealthCategory`). Quatre sondes, identifiants **constants** (décision A du 2026-11-22) :

| Identifiant | Mesure | Statuts par défaut |
|---|---|---|
| `data.connection` | la connexion Doctrine par défaut répond à une requête triviale, avec sa durée | `ok` ; `warning` au-delà de 500 ms ; `critical` si la requête échoue (message masqué, jamais le DSN) |
| `data.pending_migrations` | migrations Doctrine connues mais non exécutées (`doctrine/migrations`, déjà requis par Sylius) | `ok` à zéro ; `critical` dès une ; `warning` pour une migration exécutée inconnue du code |
| `data.schema_drift` | écart entre le schéma attendu par le mapping et la base (`SchemaTool::getUpdateSchemaSql`) | `ok` sans écart ; `warning` avec le **nombre** d'instructions ; `unknown` si le calcul dépasse son budget de temps |
| `data.table_growth` | nombre de lignes **estimé** des tables déclarées (catalogue MySQL `information_schema.TABLES.TABLE_ROWS`, PostgreSQL `pg_class.reltuples`), jamais de `COUNT(*)` | `ok` sous le seuil ; `warning` au-delà ; `critical` au-delà du double ; `unknown` pour une plateforme non gérée |

### Règles

- **Seuils configurables, défauts opinionnés** (question n° 3 d'EPIC-21, même règle qu'US-293 : chaque sonde porte ses seuils).
- `data.table_growth` ne surveille que les tables **déclarées** en configuration (`table_growth: {tmonier_audit_log: 100000, …}`) ; sans déclaration, elle rend `ok` « aucune table surveillée ». La démo déclare les tables purgées par ses crons (journal d'audit, envois de webhooks, journal PunchOut).
- `data.schema_drift` affiche le **nombre** d'instructions, jamais leur SQL (noms de tables et colonnes : information interne, règle 5 d'EPIC-20).
- Budget de temps de l'exécuteur appliqué (règle 1 d'EPIC-20) ; résultat mutualisé par le cache de la page ; lecture seule : aucune sonde n'exécute de migration ni ne corrige le schéma.
- Lien d'action vers la documentation du plugin (commande à lancer : `doctrine:migrations:migrate`, `doctrine:schema:validate`), pas d'URL externe.

Hors périmètre : taille des tables en octets, index manquants, réplication, plusieurs connexions Doctrine (seule la connexion par défaut est sondée).

## Critères d'acceptation

```gherkin
Fonctionnalité: Sondes de données

  Scénario: Base saine (nominal)
    Étant donné une base qui répond en moins de 500 ms, toutes les migrations exécutées, un schéma conforme au mapping et des tables déclarées sous leur seuil
    Quand les quatre sondes de données s'exécutent
    Alors toutes rendent « ok »

  Scénario: Migration oubliée (alternatif)
    Étant donné deux migrations présentes dans le code et non exécutées
    Quand la sonde « data.pending_migrations » s'exécute
    Alors elle rend « critical » avec « 2 migrations en attente »
    Et son lien d'action mène à la documentation de la commande de migration

  Scénario: Table qui grossit sans purge (alternatif)
    Étant donné une table déclarée avec un seuil de 100 000 lignes et une estimation de 150 000
    Quand la sonde « data.table_growth » s'exécute
    Alors elle rend « warning » avec le nom de la table et l'estimation
    Et aucune requête COUNT(*) n'est exécutée

  Scénario: Base injoignable (erreur)
    Étant donné une connexion qui lève une exception portant le DSN
    Quand la sonde « data.connection » s'exécute
    Alors elle rend « critical »
    Et ni le DSN, ni l'hôte, ni le mot de passe n'apparaissent à l'écran
    Et aucune exception ne remonte à la page

  Scénario: Calcul de dérive trop long (erreur)
    Étant donné un calcul de dérive du schéma qui dépasse son budget de temps
    Quand la sonde « data.schema_drift » s'exécute
    Alors elle rend « unknown » avec le motif « calcul interrompu »
    Et les autres sondes de la page rendent leur résultat
```
