# US-309 — Historique : instantané périodique, frise par sonde sur 30 jours, purge configurable

> Epic : [EPIC-23](../epics/EPIC-23.md) · Persona : Didier (DSI) ; Hugo (intégrateur Sylius) · MoSCoW : **Must** · Points : **5** · Sprint : **[sprint 61](../../sprints/sprint-61-historique-symfony-ci/sprint-goal.md)** · Statut : **ready-for-dev**
> Origine : EPIC-23, plus petite version livrable (historique retenu dès la première version le 2026-11-22). Dépend d'[US-307](US-307.md) (mesure sans cache, `Verdict`). Dépôt : `sylius-platform-health-plugin`, release v0.7.0 ; démo en `^0.7` dans T-309-05. US-310 (alertes à la transition) dépend de cet historique.

## Story

En tant que DSI, je veux voir sous chaque sonde son statut des trente derniers jours, afin de savoir si un avertissement qui dure empire, s'améliore ou revient, sans tenir moi-même un tableau des relevés.

## Contexte

- **Décisions de Thibaut du 2026-11-28** :
  1. Le relevé est fait par une **commande** `tmonier:health:record`, lancée par le cron de l'hôte (horaire dans la démo). Il ne dépend donc pas des visites. La même commande purge.
  2. Une ligne stocke **le statut seul** : identifiant, catégorie, statut, date. **Aucun résumé**, comme pour le niveau détail HTTP (US-308), parce qu'un résumé peut citer une version ou un nom de table.
  3. La « courbe » est une **frise d'une case par jour**, avec le pire statut du jour. Elle est rendue côté serveur, sans JavaScript ni bibliothèque tierce.
  4. **Rétention de 30 jours par défaut**, configurable.
- Table `tmonier_platform_health_record` : `id`, `identifier` (64), `category` (32), `status` (16), `recorded_at` (`datetime_immutable`), index (`identifier`, `recorded_at`). Mapping XML sous `config/doctrine`, écriture par DBAL comme `DbalHeartbeatStore`, migration du plugin.
- Volume attendu : 23 sondes × 24 relevés × 30 jours, environ 16 500 lignes.
- Configuration `tmonier_sylius_platform_health.history` : `retention_days` (30 par défaut, minimum 1).
- La commande mesure **sans cache** (le relevé ne doit pas reprendre le cache d'une page vue juste avant). Elle écrit une ligne par sonde à la même date, puis supprime les lignes plus anciennes que `retention_days`. Le relevé suit la même règle que le reste du plugin : une sonde qui lève une exception est relevée `unknown`, elle ne casse pas le relevé.
- La frise montre les 30 derniers jours, jour courant compris, dans le fuseau de l'application. Chaque case porte le **pire** statut du jour (`critical` > `warning` > `unknown` > `ok`) ; un jour sans relevé est une case distincte « aucun relevé ». Elle se déplie sous la sonde, comme le détail existant, et se lit sans couleur grâce à un texte par case (date et statut).
- Accès : celui de la page (`access.role`). L'historique n'est exposé ni par HTTP ni par la commande `check`.
- **Démo** (T-309-05) :
  - relevé du `doctrine:schema:update --dump-sql` de production en lecture seule avant le premier test (règle 35) ;
  - ligne horaire dans `docker/crontab` avec son battement (17 commandes) ;
  - migration du plugin au preDeploy ;
  - test de la page ;
  - `proof.json`.

### Tableau de cas (A-58-4)

| Situation | Résultat attendu |
|---|---|
| premier relevé, aucune ligne | une ligne par sonde, frise : 29 cases « aucun relevé » et le jour courant |
| relevés `ok` à 10 h et `warning` à 11 h le même jour | case du jour `warning` |
| `unknown` et `ok` le même jour | case `unknown` |
| `critical` et `warning` le même jour | case `critical` |
| ligne de J-30 (bord de la fenêtre) | gardée par la purge si `retention_days` = 30, hors frise de 30 jours (J-29 à J) |
| ligne de J-31 | supprimée par la purge |
| sonde qui lève une exception pendant le relevé | ligne `unknown`, le relevé continue et la commande sort en 0 |
| base injoignable pendant le relevé | aucune ligne, message d'erreur, code de sortie 1 |
| sonde retirée depuis | ses lignes restent jusqu'à la purge, aucune frise sans sonde affichée |
| `retention_days: 0` | configuration refusée au démarrage |

## Critères d'acceptation

```gherkin
Fonctionnalité: Historique des sondes de santé

  Scénario: Relevé horaire (nominal)
    Étant donné le plugin de santé installé et sa migration exécutée
    Quand le cron lance "tmonier:health:record"
    Alors une ligne par sonde est écrite avec son identifiant, sa catégorie, son statut et la date du relevé
    Et aucune ligne ne contient de résumé

  Scénario: Frise sur 30 jours (nominal)
    Étant donné des relevés sur les 30 derniers jours
    Quand Sophie déplie une sonde sur la page de santé
    Alors elle voit 30 cases, une par jour, portant le pire statut du jour
    Et chaque case se lit sans couleur (date et statut en texte)

  Scénario: Jour sans relevé (alternatif)
    Étant donné un jour où le cron n'a pas tourné
    Quand la frise est affichée
    Alors la case de ce jour indique « aucun relevé », distincte d'un statut

  Scénario: Purge configurable (alternatif)
    Étant donné "history.retention_days" à 30 et des lignes de 31 jours
    Quand "tmonier:health:record" s'exécute
    Alors les lignes de plus de 30 jours sont supprimées et celles de J-30 sont gardées

  Scénario: Sonde défaillante (erreur)
    Étant donné une sonde qui lève une exception
    Quand le relevé s'exécute
    Alors sa ligne est "unknown", les autres sondes sont relevées et la commande sort en 0

  Scénario: Accès refusé (erreur)
    Étant donné un administrateur sans le rôle "access.role"
    Quand il demande la page ou le composant qui porte la frise
    Alors il reçoit 403, comme pour la page sans historique
```
