# US-291 — Santé de la plateforme : accessibilité AA, statut jamais porté par la seule couleur, mode sombre

> Epic : [EPIC-20](../epics/EPIC-20.md) · Persona : Nadia (responsable e-commerce B2B) ; Didier (DSI) · MoSCoW : **Must** · Points : **3** · Sprint : **[sprint 57](../../sprints/sprint-57-sondes-et-securite/sprint-goal.md)** · Statut : **ready-for-dev**
> Origine : demande de Thibaut du 2026-11-22. Dépend d'[US-288](US-288.md). Bloque [US-292](US-292.md) (captures et README décrivent l'écran final). Cible : **WCAG 2.2 niveau AA** (pas AAA : la cible du plugin est celle du thème).

## Story

En tant qu'administrateur qui ne distingue pas le rouge du vert, ou qui utilise un lecteur d'écran, je veux lire l'état de chaque catégorie et de chaque sonde sans dépendre de la couleur, afin qu'un écran dont c'est la raison d'être de signaler un problème le signale à tout le monde.

## Contexte

Un écran de supervision est le cas d'école de l'accessibilité par la couleur : pastille verte, orange, rouge. Six points, relevés sur le code d'US-288 (`templates/admin/_summary.html.twig`, `summary.html.twig`) :

1. **Le statut est toujours écrit** (« OK », « Attention », « Critique », « Non mesurable ») **et** porté par une icône de forme distincte par statut ; la couleur n'est qu'un renfort (WCAG 1.4.1). Les icônes décoratives sont `aria-hidden`.
2. **Le détail par sonde est un tableau annoncé** : `<table>` avec `<caption>` (la catégorie), en-têtes `<th scope="col">` (sonde, statut, résumé, action), un `<th scope="row">` par sonde ; le détail replié est un `<details>`/`<summary>` natif (clavier, lecteur d'écran) plutôt qu'un composant maison.
3. **Le rafraîchissement est annoncé** : le bouton « Rafraîchir » a un nom accessible, passe en `aria-busy` pendant le calcul, et le résultat est annoncé dans une région `role="status"` (politesse `polite`) sans déplacer le focus ; le focus reste sur le bouton après le rendu différé.
4. **Contrastes** (1.4.3 et 1.4.11) : texte 4,5:1 minimum, pastilles et icônes 3:1 minimum, **en clair et en sombre**. Les valeurs sont **mesurées**, pas estimées : les couleurs de chaque statut viennent de jetons nommés, et un test calcule le rapport de contraste de chaque paire jeton/fond.
5. **Mode sombre** : l'administration de Sylius 2 utilise Tabler, qui bascule par `data-bs-theme="dark"` ; les couleurs de statut du plugin sont des variables CSS qui suivent ce réglage, sans valeur en dur dans les gabarits.
6. **Clavier et mouvement** : tout est atteignable au clavier dans l'ordre visuel ; le lien d'action de chaque sonde a un nom explicite (« Corriger : 7 produits sans prix », pas « Cliquer ici ») ; le squelette de chargement respecte `prefers-reduced-motion`.

Cet audit s'applique à la page et, si [US-289](US-289.md) est livrée, à l'encart du tableau de bord (la présentation d'un statut est partagée : une macro Twig commune). Hors périmètre : AAA, droite à gauche, préférence de contraste forcée (`forced-colors`) au-delà d'un contrôle manuel.

## Critères d'acceptation

```gherkin
Fonctionnalité: Accessibilité AA de la page de santé

  Scénario: Statut lisible sans la couleur (nominal)
    Étant donné une page avec une catégorie « critical », une « warning », une « ok » et une « unknown »
    Quand le rendu est analysé sans feuille de style
    Alors chaque statut est écrit en toutes lettres à côté de sa catégorie et de chaque sonde
    Et deux statuts différents ne partagent ni le même texte ni la même icône

  Scénario: Tableau annoncé au lecteur d'écran (alternatif)
    Étant donné le détail d'une catégorie de trois sondes
    Quand le rendu HTML est analysé
    Alors la table a une légende, des en-têtes de colonne avec scope="col" et un en-tête de ligne par sonde
    Et le détail replié s'ouvre au clavier

  Scénario: Contrastes mesurés en clair et en sombre (alternatif)
    Étant donné les jetons de couleur de chaque statut
    Quand le test calcule le rapport de contraste avec le fond clair puis avec le fond sombre
    Alors le texte atteint au moins 4,5:1 et les icônes et pastilles au moins 3:1 dans les deux modes

  Scénario: Rafraîchissement sans perte de contexte (erreur)
    Étant donné un administrateur qui actionne « Rafraîchir » au clavier
    Quand le rendu différé se termine
    Alors le focus reste sur le bouton
    Et la région d'état annonce « Résultats mis à jour » sans interrompre la lecture en cours

  Scénario: Une couleur de statut ne passe pas le contraste (erreur)
    Étant donné un jeton de couleur qui donne 2,8:1 sur le fond sombre
    Quand la suite de tests est lancée
    Alors le test de contraste échoue en nommant le jeton, le fond et le rapport mesuré
```

## Definition of Done

- [ ] Statut écrit et icône distincte par statut sur la page (et sur l'encart s'il est livré) ; icônes décoratives `aria-hidden`
- [ ] Tableau avec `<caption>`, `scope`, détail en `<details>` natif ; région `role="status"` et `aria-busy` pour le rafraîchissement
- [ ] Jetons de couleur en variables CSS suivant `data-bs-theme` ; **test de contraste calculé** (clair et sombre) qui échoue sur un jeton fautif (c'est lui, le rouge prouvé)
- [ ] Revue manuelle (clavier seul, lecteur d'écran, `prefers-reduced-motion`, capture en mode sombre) consignée dans la PR : constat, pas déclaration
- [ ] Rouge prouvé en CI sur une assertion avant chaque correctif, **suites unitaire et non unitaire** (règle 26) ; CI verte Sylius 2.2/2.3
- [ ] PHPStan, ECS et Rector sur `src` **et** `tests`, lancés dans Docker (règle 28)
- [ ] CHANGELOG ; aucun tag sans GO de Thibaut
