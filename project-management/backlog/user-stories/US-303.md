# US-303 — Sondes facultatives : un plugin fournit sa sonde sans dépendre du plugin de santé

> Epic : [EPIC-22](../epics/EPIC-22.md) · Persona : Hugo (intégrateur Sylius) ; Thibaut (mainteneur des plugins) · MoSCoW : **Must** · Points : **5** · Sprint : **[sprint 59](../../sprints/sprint-59-console-sondes-schema/sprint-goal.md)** · Statut : **done**
> Origine : règle d'inversion d'EPIC-22, arbitrée par Thibaut le 2026-11-22 (`suggest`, plus une vérification de l'existence de la classe à la compilation). Reportée du sprint 58 par Thibaut le 2026-11-25. Dépend d'[US-287](US-287.md) (contrat). Bloque US-304 à US-306.

## Story

En tant qu'intégrateur, je veux qu'un plugin comme `webhook-outbox` fournisse sa sonde de santé sans m'imposer le plugin de santé, afin d'installer un plugin de webhooks sans tableau de bord de santé, et de voir sa sonde apparaître dès que j'ajoute le plugin de santé.

## Contexte

Le plugin de santé est le propriétaire du contrat (`HealthCheckInterface`, `HealthResult`, `HealthCategory`). Une sonde est découverte par autoconfiguration : tout service qui implémente l'interface reçoit le tag `tmonier_platform_health.check`. Si `webhook-outbox` mettait le plugin de santé en `require`, installer des webhooks imposerait un écran de santé : c'est refusé pour dix plugins publiés sur Packagist.

### Mécanisme

1. Le plugin surveillé déclare le plugin de santé en **`suggest`** et en **`require-dev`** (pour ses tests), **jamais en `require`**.
2. Ses sondes vivent dans un fichier de services à part (`config/health_checks.php`). Son extension ne charge ce fichier **que si `HealthCheckInterface` existe** (`interface_exists`, à la compilation du conteneur). Sans le plugin de santé, la classe de sonde n'est jamais chargée par l'autoloader, ce qui évite une erreur fatale sur une interface absente.
3. Sans sonde, rien ne s'affiche : une catégorie qui n'a aucune sonde est **masquée** sur la page et dans l'encart, jamais affichée vide ni en erreur.
4. Le plugin de santé documente le motif (README EN/FR, exemple complet) et l'applique dans son application de test à un **plugin de démonstration** (`tests/Fixture`), dont la vérification d'existence est injectable. Le test peut ainsi booter un conteneur où l'interface « n'existe pas », ce qu'un `interface_exists` réel ne permettrait pas dans ce dépôt.

Hors périmètre : les sondes des plugins B2B (US-304 à US-306), l'ordre d'affichage des catégories.

## Critères d'acceptation

```gherkin
Fonctionnalité: Sondes fournies par un plugin, plugin de santé facultatif

  Scénario: Plugin de santé installé (nominal)
    Étant donné le plugin de démonstration et le plugin de santé
    Quand le conteneur est compilé
    Alors la sonde du plugin de démonstration porte le tag des sondes
    Et elle s'affiche sur la page dans sa catégorie

  Scénario: Plugin de santé absent (alternatif)
    Étant donné le plugin de démonstration dont la vérification dit que l'interface n'existe pas
    Quand le conteneur est compilé et le noyau démarre
    Alors aucune erreur n'est levée
    Et le conteneur ne contient aucun service de sonde du plugin de démonstration

  Scénario: Catégorie sans sonde (alternatif)
    Étant donné une catégorie qui n'a aucune sonde enregistrée
    Quand la page et l'encart du tableau de bord s'affichent
    Alors la catégorie n'apparaît ni sur l'un ni sur l'autre

  Scénario: Sonde fournie qui échoue (erreur)
    Étant donné une sonde du plugin de démonstration qui lève une exception
    Quand la page s'exécute
    Alors la sonde rend « unknown », la cause est journalisée, et les autres sondes s'affichent

  Scénario: Plugin surveillé publié (erreur)
    Étant donné le composer.json du plugin de démonstration
    Quand on le lit
    Alors le plugin de santé est en suggest et en require-dev, jamais en require
```
