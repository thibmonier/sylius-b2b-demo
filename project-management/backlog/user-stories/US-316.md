# US-316 — Spike Peppol : un adaptateur de transmission vers le réseau Peppol pour einvoice-transmission

> Epic : [EPIC-14](../epics/EPIC-14.md) · Persona : Thibaut ; Hugo (intégrateur Sylius) ; Nadia (responsable e-commerce B2B) · MoSCoW : **Should** · Points : **3** · Sprint : à planifier · Statut : **backlog**
> Origine : demande de Thibaut du 2026-11-23 (plugins complémentaires utiles à la communauté). Dépendances : aucune ; s'appuie sur le port `InvoiceTransmitterInterface` du plugin `einvoice-transmission` ([ADR-0016](../../../docs/adr/0016-facture-electronique-pa-pdp.md)) et sur l'adaptateur Pennylane ([US-283](US-283.md)) comme modèle.

## Story

En tant que mainteneur des plugins de facture électronique, je veux savoir ce qu'exige un adaptateur Peppol du port `InvoiceTransmitterInterface`, afin de décider en connaissance de cause s'il faut créer un plugin `einvoice-peppol` qui rend la chaîne Factur-X utilisable hors de France, ou ne rien créer.

## Contexte

Timebox **6 h**. Le port existe (`transmit(InvoiceDocument): TransmissionResult`, journal des envois et statuts dans `einvoice-transmission`) ; Pennylane en est le premier adaptateur réel. Peppol est le réseau européen d'échange de factures. Il est donné comme support de l'obligation B2B belge et de l'interopérabilité entre plateformes agréées françaises : ces deux affirmations sont **à vérifier** par le spike, pas des faits établis.

Questions, chacune avec une source officielle datée :

1. **Obligations** — quels pays imposent ou acceptent Peppol pour la facture B2B, depuis quand (Belgique, Allemagne, France via les PA, autres) ? Sources : SPF Finances, OpenPeppol, DGFiP.
2. **Format** — Peppol BIS Billing 3.0 accepte-t-il le CII de Factur-X, ou faut-il produire de l'UBL ? Si UBL : une conversion CII → UBL fiable existe-t-elle en PHP (bibliothèque maintenue, licence compatible MIT), ou faut-il générer l'UBL depuis la commande ? Quelles règles de validation (Schematron) appliquer avant l'envoi ?
3. **Point d'accès** — un émetteur ne se connecte pas seul au réseau : il passe par un point d'accès certifié. Le plugin cible-t-il une API de fournisseur de point d'accès (lesquels publient une API documentée et un bac à sable gratuit) ou un protocole neutre ? Comment éviter de lier le plugin à un seul fournisseur (adaptateur par fournisseur, comme Pennylane) ?
4. **Identifiants** — schémas d'identifiant Peppol des participants (SIREN, numéro d'entreprise belge, TVA) : où les lire dans Sylius (Factur-X par channel, `company-accounts`, `company-verification`) ? Comment vérifier qu'un destinataire est inscrit (SMP / annuaire Peppol) avant l'envoi ?
5. **Statuts** — les réponses Peppol (Invoice Response, Message Level Response) se rangent-elles dans les statuts du journal d'`einvoice-transmission` sans changer son modèle ?
6. **Écosystème** — un plugin Sylius ou un bundle Symfony Peppol existe-t-il déjà sur Packagist ou le Sylius Store ? Recoupement Sylius Plus : politique inchangée, pas de promotion en cas de recoupement.

Règles transverses : ton neutre, aucune promesse de conformité, sources et dates de consultation citées ; une affirmation non confirmée est marquée « non confirmée » et exclue de toute formulation publique.
